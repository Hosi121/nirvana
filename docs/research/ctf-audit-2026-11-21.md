# 公開CTFのC／x86-64入力調査

2026-11-21の測定記録です。以下の数値・障害は記載したrevisionの結果で、現在の開発計画は[ロードマップ](../x86-64-roadmap.md)にあります。

Nirvana [`3730adf`](https://github.com/Hosi121/nirvana/tree/3730adf648b90ce4e914269adcbc1801d8ee974c) に、公式配布のELF64／x86-64を入力した結果。
Cソースが公開されたrev 3問・pwn 3問を、制御移転・メモリ・外部効果の違いから選んだ。
出典revision、配布バイナリとソースのSHA-256、入口、測定用の関数は[corpus manifest](../../tools/corpora/ctf-x86-64.json)に固定した。

## 結果

`main`を入口にした`module-locals-c`は6問とも途中で停止した。
最初の障害はCOPY再配置が3問、FSによるTLSアクセスが2問、連続RAM画像の上限が1問だった。
選んだ20関数の1,116命令をGNU objdumpの命令境界で照合すると、未対応7命令はすべてFSアクセスだった。
この照合は個別命令のデコード検査で、到達性・CFG・実行意味の対応は各段階で評価する。

数値はリンク時アドレス。PIEの実行モデルでは既定bias `0x10000`を加える。
`sheep`は公式の`publish/sheep`が指す`src/sheep`を測定した。
表の切出しは元ELFの関数バイト列を使う単一関数の診断であり、ELF全体の読込みとは分けて集計した。
単一関数経路のCALL拒否と、module経路のCALL対応も区別している。

## 入口対応後の比較

[`e6e5b5e`](https://github.com/Hosi121/nirvana/tree/e6e5b5e9811fa32d1cb6a8de55b512aef395ebd1)で、同じSHA-256の6問を再測定した。
`main`からのC生成は0/6から5/6へ進み、その5問はC11の警告をエラーにしたコンパイルも通った。
flat／readable／localsの3出力、合計15個について、`-O2`とUBSanを付けたコンパイルを確認した。

入口を塞いでいた標準streamのCOPY／GOT別名、`FS:0x28`のstack guard、ENDBR64／BND付きPLTを扱った。
COPY先とGOT参照を同じゲスト変数に結び付け、guardも更新可能なRAM slotとして表現する。
生成Cの`puts`はゲストの`stdout`変数を読み、`stdout = stderr`後の出力先と返り値を自作バイナリで照合した。
命令照合は従来と同じ1,116命令で、scalar 1,109命令と明示的FS guard profileの7命令に分かれる。

`jmp flag`は集計した局所値の保存量の上限により131関数がレジスタ表現へfallbackし、`pwnymalloc`にも1関数のfallbackがある。
残る`wrong signal`には疎なマッピング・ページ権限・signalの対応が必要になる。
既存9ケースのモデル実行結果は一致し、`jmp flag`の計算された戻り先は引き続き`UnknownTarget(0x112b6)`になる。
今回の指標はC生成とコンパイルで、外部関数を含む全体のネイティブ実行比較、未知の正解を生成Cから求める評価は次の段階で行う。

検証はRustの164 target・1,181 test成功（任意検証20件ignored）、Clippy、fmt、Python 41件成功・1件skip。
Rustは全target実行後、標準stream adapterの修正に関係する5 targetを再実行した。
比較値・診断・入力hashは[生成対応後のJSON](../../tools/corpora/ctf-x86-64-generation.json)に保存した。

## summarizeの外部I/Oを含む実行比較

[`7c65e30`](https://github.com/Hosi121/nirvana/tree/7c65e304d45f5a56756ef1df6632687a195b1404)で`putchar`、整数・文字列の`printf/sprintf/snprintf`、整数の`scanf`を共通adapterへ追加した。
GP registerからstackへ続く可変長引数と、最適化で使われるfortify版の引数位置を扱う。
適用する書式・上限・fault順序は[実行モデル](../equivalence.md)にある。

同じ配布バイナリの`main`から生成したCを実行すると、公開された正解例はflag表示まで到達した。
正解例・ゼロ入力・6個の引数変異を、3出力×O0/O2で比較し、**48/48で終了コード・stdout・stderrが一致**した。
変更前の生成Cは、同じ正解入力でも先頭メッセージの後にunsupported（status 3）で停止していた。
入力は既知の正解と変異から作った回帰評価で、未知の正解を求める評価には別の入力集合を使う。

元ソースは`scanf`の返り値を確認せず、失敗時に局所変数を未初期化のまま読む。
空入力・不正token・途中EOFの3例は参考観測へ分けた。
EOF・部分成功・代入幅は、初期値を持つ[fixture](../../tests/fixtures/formatted-io.c)でGCC O0/O2×EXEC/PIEを使い、生成Cとの192比較で確認した。
別のABI harnessはstack引数、buffer境界、切詰め、pointerのalias、未対応書式の停止を検査する。
入力hashと結果は[stdio比較JSON](../../tools/corpora/ctf-x86-64-stdio.json)に保存した。

```sh
python3 tools/audit_ctf_stdio.py --inputs target/ctf-audit/inputs --output target/ctf-stdio
```

## 疎な画像の読込み後の比較

[`ae32582`](https://github.com/Hosi121/nirvana/tree/ae32582af6b4e424f8613458d99e033520c67f8c)で、同じ6問のC生成・C11コンパイルは**5/6から6/6**になった。
3出力×6問の18個は`-O2`・UBSan付きのコンパイルも通過した。
`wrong signal`はruntimeを含む仮想範囲319,189,056 byteを、48個の範囲と1,018,285 byteのbackingへ保持する。
元のポインタと分岐先を維持し、各アクセスの穴・権限・全幅をRust／Cの両方で検査する。

範囲の隣接・権限境界・overflowと、EXEC/PIEの全PCからの再開を3出力で比較した。
初期化・GOT・表の探索も同じ対応表を使う。既存9個のモデル実行と`summarize`の48個のネイティブ比較は結果を維持した。
新しい生成Cを実行すると、最初の未対応importは`memset`で、部分状態付きのstatus 3になる。
この問題の検査全体を動かすには、追加libc adapterとsignal handlerへの移転が必要になる。
適用範囲は[疎なメモリの実行契約](../equivalence.md)、入力hash・診断・生成物hashは[比較JSON](../../tools/corpora/ctf-x86-64-sparse.json)にある。

画像のprofileと使用量は次で取得できる。

```sh
cargo run --example inspect_ctf -- image path/to/ELF 0x4011a0
```

## 制御とメモリで分かったこと

`jmp flag`の`process(65)`は、モデル内で25命令後に`UnknownTarget(0x112b6)`へ到達した。
間接JMP先の関数本体へは進めるが、そのRETが戻る`process`内部のPOP／RETを発見できていない。
`module-jumps`も`complete:false`で、表候補は0件だった。
この例は、通常CALL以外の方法で作る戻り先をコード発見へ結び付ける評価入力になる。

`wrong signal`のPT_LOAD合計は952,685 bytes、最小から最大までのアドレス幅は`0x13057000`、約304 MiBある。
現在の連続RAMモデルには、疎なマッピングとページ権限を保持する拡張が必要になる。
ソースのvolatile LoadとSIGSEGV handlerを扱うには、メモリfaultからhandlerへの移転も観測契約に加える。

`baby-talk`は、呼出し先のメモリ効果を追う具体例になる。`strtok`は入力bufferを書き換え、次回呼出し用の位置も保持する。
`pwnymalloc`は、同じ領域を使用中のデータとfree listの管理情報に使い分ける。
Storeの到達定義に、領域の世代・用途、calleeのread/write集合を組み合わせる評価対象として使える。
これらの追加課題はソースと現在の実行モデルからの設計判断で、mainの最初の障害を越えた成功率とは個別に扱う。

## 次の実装順序

1. **一般Cの入口を広げる**：COPY再配置の外部データ、TLS／stack canary、標準ライブラリ参照を解析用IRへ表現する。
2. **外部呼出しの効果を分ける**：未知CALLの表示と、検査付き実行に必要な環境モデルをそれぞれ持つ。`printf/scanf/read`と`malloc/free/strtok`が今回の具体的な対象になる。
3. **メモリと制御の追跡を広げる**：MemorySSA・alias・領域の世代と、計算された分岐先／戻り先の発見を、このcorpusで比較する。
4. **例外を伴う実行モデルを追加する**：疎なマッピング、ページ権限、signalを専用の観測契約で検証する。

## 再現

Rust、Python 3、Cコンパイラ`cc`、GNU binutilsの`readelf/objdump`を使う。初回はGitHubから入力を取得する。

```sh
cargo build --locked --bin nirvana --example inspect_ctf
python3 tools/audit_ctf.py --output target/ctf-audit
python3 tools/audit_ctf.py --output target/ctf-audit --offline
```

入力27ファイルは1,163,373 bytes。取得時と再利用時にSHA-256を照合する。
静的解析、個別命令の照合、生成できたmainと関数単位のC11コンパイル、9ケースのNirvanaモデル実行を行う。
`summarize`の正解例は公開ソースの例を使い、10882命令後の`Returned(1)`を観測した。
今回の動作観測はRust moduleモデルの返り値・停止PCで、原配布プログラムと生成Cのネイティブ比較は追加評価項目である。
同じ測定を新しい保存先への取得から繰り返し、結果の一致を確認した。

コマンド・診断・生成物は指定した保存先、比較用の集計は[baseline JSON](../../tools/corpora/ctf-x86-64-baseline.json)にある。
第三者のバイナリとソースはローカルcacheへ取得し、repositoryにはmanifest・測定器・結果を置く。
この6問は構造に基づく目的抽出であり、CTF全体での出題頻度や一般的な成功率は、追加corpusで評価する。
