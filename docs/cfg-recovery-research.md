# CFG復元とコンパイラ最適化

2026-11-20調査。対象は`e5e9fcb`。次の実装対象を選ぶため、論文・実装とNirvanaの境界を整理した。
以下の優先順位・検証計画は提案で、改善量は実装後に比較する。

## 現在の足場

| 対象 | 既存の処理 | 次に扱う範囲 |
| --- | --- | --- |
| ループ回転 | [guarded_loop](../src/guarded_loop.rs)が純粋な入口判定と末尾判定を初期値の事実で照合し、while/for表示へ接続 | 入れ子、途中continue、メモリを読む条件を含む回転 |
| 共通末尾 | [structure](../src/structure.rs)がブロックの複製数を制限し、後支配関係と前向きDAGから共有先を選択 | 構造化が失敗した領域を特定し、その周辺で分割・複製を提案 |
| 複数入口の循環 | 構造化は`Irreducible`を返し、C出力はgoto経路を選択。module出力も関数単位で退避 | 難しい領域にgotoを置き、外側のif/loopを維持 |
| 展開ループ | [loop_recover](../src/loop_recover.rs)が加算ループ候補を有限・アフィン領域検査で採用 | 複数の誘導変数、一般の反復数、メモリを含む本体 |
| 間接分岐 | CFGに未知の辺を保持。module IRは動的Transferを実行 | テーブル由来の関数内ターゲットの発見と複数辺の解析 |

単純なガード付き回転ループの表示は実装済みである。追加開発は上表の拡張と比較を対象にする。
moduleの動的Transferは、直接到達先からの命令発見や構造化用の関数内CFGとは別に扱われる。

## 研究から得た判断材料

[SAILR §4–7][sailr]は、構造化で現れたgotoの周辺からコンパイラ変換を探し、複製された処理の集約と、共有された処理の複製を使い分ける。
元ソースへの構造的な近さを評価し、goto数・行数に加えて、領域ごとのグラフ編集距離を用いる。
同論文のISD/ISCという名前は文の複製・集約の分類であり、グラフ理論の既約性とは区別する。
呼出しごとの復帰情報もCFGの辺に影響するため、import効果の拡張時には正常復帰先を対応付ける。

参照した[angrのCrossJumpReverter][crossjump]は、goto先の単一後続ブロックを複製する。
反復数とcallの複製数に上限があり、入力グラフのコピーに対して候補を作る。
これは探索と静的な出力量を制御する参考になる。

[LLVMのループ回転][rotation]では、ヘッダの処理と判定を複製し、必要に応じて入口ガードを残す。
[Jump Threading][threading]では、先行経路から分岐結果が分かる場合にブロックを複製して辺をつなぎ替える。
したがって、命令列の形と一緒に、各経路で成立する値の関係を照合する必要がある。

[Ddisasmのテーブル解析][tables]は絶対・相対アドレスの候補を区別し、命令との重なりやコードとしての解釈で候補を絞る。
[相対テーブルの実装][relative]では、エントリ幅、基準アドレス、差分の符号や加減算方向も扱う。
Nirvanaでも、表のbyte列とターゲットを計算する式を対応付ける設計が適していると考える。

## Nirvanaへの適用案

### 領域単位で候補を作る

最初の実装対象には、構造化の失敗箇所の診断と、共有末尾の制限付き複製を選ぶ。
現在は既約性検査で関数全体の構造化を終えるため、この境界に改善の余地がある。

1. 失敗した辺、循環の入口、合流先、複製上限に達した場所を記録する。
2. 支配・後支配関係と強連結成分から候補領域を選ぶ。複数入口・複数出口は明示的に保持する。
3. その領域で短い末尾を複製する候補と、局所gotoを持つ候補を作る。
4. 元のStep・条件・辺との対応を検査し、出力量の予算内で構造を改善する候補を選ぶ。

候補には対象領域、元PCとコピーの対応、入口・出口、前提、コスト、検査結果を添える。
各変更後に必要な支配関係・SSA・生存情報を再構築する。
callやStoreを静的に複製する候補も、各動的経路での実行回数・引数・順序を対応させる。
同じ保存場所を使う式の照合には、その時点のSSA定義とメモリの状態を使う。

最初は元の操作と判定を保持した配置変更を対象にする。
次段階で、純粋な経路条件の含意を使う集約や条件の再構成を追加する。
条件の複雑さ、字下げ、局所goto、静的なコピー数を別々に測り、候補間の利点を確認する。

### 間接分岐を段階的に回復する

最初の対象は、リンク済みx86-64 ELF内の範囲検査付きジャンプテーブルとする。
PIEで使われる符号付き32-bit相対エントリと、絶対アドレスの表を個別に認識する。

解析情報は次の三つに分ける。

- 実行時にターゲットを得る元の式と、そのLoadの幅・評価順。
- 画像と値域から導出したターゲット候補集合。
- 集合が全実行を覆うという根拠、または残る未知の辺。

先行する範囲検査は対象の分岐を支配し、添字の定義・幅・符号解釈が対応することを確認する。
テーブルの参照先が分かれば追加命令をデコードし、関数境界と重なりを検査して解析を更新する。
重複したcase先、defaultと同じ先、負の相対差分、画像の再配置も保持する。

現在のゲストRAMは書換え可能なので、ELFの初期テーブルから得た候補は実行中の全候補とは限らない。
完全性の採用には、許される初期状態とStore・外部callからテーブルが保護される根拠が必要になる。
実行は実際のゲストRAMから分岐先を評価し、候補外の先には動的な退避経路または未対応の診断を保つ。
完全性が確認できた閉じたCFGを、全体の支配解析やswitch構造化へ渡す。
core IRは現在Next/Jump/Branch/Returnを持つため、複数ターゲットの表現と実行・検査器まで一緒に設計する。

### 検査の対象を変換ごとに決める

| 候補 | 検査する対応 |
| --- | --- |
| コピーの配置・局所goto | 元PCへ戻したStep列、代入と条件の評価、break/continue先。moduleでは途中PCからの再開と命令予算も確認 |
| 純粋な条件の再構成 | 対応するSSA値、経路条件の含意、u64の折返しとシフト規則、終了・反復の対応 |
| メモリを含む移動・集約 | Load/Store/callの順序・回数、最初のfaultとその前の全RAM・外部効果 |
| 反復数を変える巻戻し | 導出した入力域、反復の対応、領域出口の値。trace・途中再開・命令予算の扱いを採用条件に含める |

[structure_verify](../src/structure_verify.rs)は元の式・代入と制御の対応を検査する。
条件の追加・除去には、その検査に加えて意味上の根拠を持たせる。
有限・アフィン領域の既存証拠は、定義された純粋領域の正常出口を対象とする。
検査範囲と具体実行比較は[検証ガイド](verification.md)の区別に合わせて報告する。
[Alive2][alive2]のような反復上限付きの検査を使う場合も、上限を証拠に記録する。

## 次の比較計画

最初の比較は「共有return」「共有cleanup」「ループ脱出先の共有」「ソースにもgotoがあるcleanup」の4形状とする。
GCC/Clang × O2/O3の16構成を予定し、コンパイラ版・全フラグ・同一オブジェクトのhashを保存する。
最適化の帰属には中間ダンプを使い、フラグの有無による差は変換間の相互作用も含む観測として扱う。

意味の採用条件を満たしたうえで、元ソースと生成Cのループ・条件・出口の構造を比較する。
元ソースは評価用の参照として使い、デコンパイラへの入力はバイナリに統一する。
全関数goto退避の件数、最大条件長・字下げ、コピー数、出力量、解析時間、未判定件数を併記する。
少なくとも一つの従来退避例で外側の構造を保てるかを確かめ、全構成で意味の回帰を検査して次の拡張を判断する。
その後、ジャンプテーブル、誘導変数の対応、複製経路の集約の順に比較対象を広げる。
