# x86-64デコンパイラのロードマップ

x86-64の機械語の動作を保ち、人が関数・データ・制御の意味を追えるCを得ることを目指す。
**現在の優先段階はM0: Evaluation（進行中）**。意味の保存・入力の広さ・元ソースへの近さを同じ入力で評価し、次の実装を決める。
実装の参照点は[`ea036f2`](https://github.com/Hosi121/nirvana/tree/ea036f2)（2026-11-22）。測定結果には、その測定revisionを併記する。

## 着手順を決める

1. 対象マイルストーンと、改善したい観測を一つ選ぶ。
2. 入力・実行契約・比較対象・予算を固定し、変更前の結果を残す。
3. 実装後に同じ条件で比較し、意味の保存と回復品質を別々に判定する。
4. 結果をゲートへ戻し、採用・見送り・次の障害を記録する。

M0の完了までは、評価器の不足と、評価を通して確認した障害を解消する。
局所的な変数削減はM3の部分成果として扱い、元ソースの構造回復は構造指標で評価する。
機能追加の件数とテスト成功件数に加え、どの到達基準へ進んだかを示す。

## 段階と到達基準

以下は実装順と採用条件であり、IRを順番に別形式へ変換する一覧とは異なる。
各表現の責務と境界は[抽象化の段階と保証](architecture.md#抽象化の段階と保証)、観測契約は[実行モデル](equivalence.md)を正本にする。

| 段階 | 到達する状態・成果物 | 合格条件 |
| --- | --- | --- |
| **M0: Evaluation** | 固定corpus・hold-out・再現manifest、意味比較、元ソースとの構造比較、失敗分類を一つの報告へまとめる | 初回の24構成を全件報告し、未対応・未知・timeoutも分母に保持。評価器の正負対照を通し、baseline・各失敗段階・費用を再現できる |
| **M1: 実行IRと解析の契約** | 命令位置・幅・効果・未知辺を持つExecutable IRと、SSA/MemorySSAの根拠を対応付ける | 宣言した整数・ABIの範囲でnative、IR、再コンパイルCを比較。SSA入力・メモリ書込み候補とfault・予算・途中再開の境界を検査できる |
| **M2: Compiler-aware CFG recovery** | コンパイラ由来の複製・共有・条件変形を領域単位で戻し、候補CFG・元PC対応・検査根拠を残す | M0の開発集合とhold-outで構造距離を比較し、意味の回帰0件を維持。条件の肥大化、複製量、残余goto、解析費用を併記する |
| **M3: 意味・データの回復** | 保存値・寿命・関数間効果から、変数・型・objectとSemantic IRの候補を作る | 部分書込み・alias・escape・未知CALLを検査し、元変数/field/型の対応精度と回収率を比較。意味付き演算は検査して実行IRへ下ろす |
| **M4: Structured ASTとC** | 領域gotoを含む制御構造、φコピー・保存先・宣言・名前・型表記を統合する | ASTから戻した制御と元IRの対応を検査。生成CのO0/O2・UBSan比較を通し、M0で構造と変数の品質を確認する |
| **M5: x86-64の実用範囲** | 大きいLinux ELF、stripped入力、追加の命令・ABI・runtimeへプロファイルを広げる | 追加領域ごとにcorpusと観測契約を定義し、未対応も含む全件の回収率・意味・品質・費用を報告する |

まずM0の小さい比較を成立させ、その比較が要求するM1の契約とM2の復元を進める。
**M2はM3の型・データ復元の完成を待たずに着手する。** 既存のStructured ASTとC backendを使い、構造回復の効果を早期に測る。
M1〜M4は対象領域を広げながら反復し、M5で入力領域を拡張する。SIMD/FPや新しいABIも、対応プロファイルのM1/M0へ戻して評価する。

## M0: Evaluation

### 三つの軸

| 軸 | 観測 | 採用判断 |
| --- | --- | --- |
| 意味 | 返り値、全RAM、最初のfault。moduleはレジスタ・PC・命令予算・外部効果・途中再開も含む | 同じ契約で意味の反例0件を維持。具体実行と、モデル・前提・上限付きの証明結果を区別する |
| 入力の広さ | decode/lift、CFG発見、解析、構造化、C生成、再コンパイル、実行比較の各到達件数 | 各段階の成功・拒否・未知・予算切れ・誤出力を全入力から集計する |
| 元ソースへの近さ | 制御構造の距離、条件の規模、複製量、変数・fieldの対応。goto数・変数数・文字数は補助指標 | 同じbinaryのbaselineと候補を比較し、意味と対応範囲を維持した品質改善を採用する |

[SAILR §5・§7](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)は、コンパイラ変換を戻す処理と、元ソースへの構造的な近さを測る評価を組み合わせている。
Nirvanaでも、ソースに由来するgotoと復元で増えたgotoを区別できる参照を用意し、条件や処理の複製を含めて評価する。

構造評価の初回成果物は、元関数と生成関数から得る正規化した制御グラフと、その対応・距離・計算費用である。
正規化規則、ノード/辺のラベル、編集コスト、対象関数を版付きで固定する。runtime helperは別関数として分離し、対象関数内のdispatcherや退避gotoは評価対象に含める。
小さい領域の正確な距離と、大きい領域の近似値・上限到達を別の判定で記録する。
SAILRのCFGEDと比較する場合は同論文の領域分割・計算条件を合わせ、独自の距離には別のmetric IDを付ける。
評価器には、名前・PCラベルだけの変更で距離0となる対照と、gotoを減らしても条件や処理の複製で距離が悪化する対照を置く。

### 最初に固定する比較

開発用は[CFG調査](research/cfg-recovery-research.md)の4形状「共有return」「共有cleanup」「ループ脱出先の共有」「元ソースにもgotoがあるcleanup」を使う。
GCC/Clang × O2/O3の16構成とし、別の二つのソース族を同じ4プロファイルでhold-outへ置く。初回は合計24構成をmanifestに固定する。
既存fixtureや実OSSから選んだ関数にはソース族・revision・ライセンス・入口を記録し、同じソースの最適化違いを同じ集合に置く。
実装修正に使ったhold-outは開発用へ移し、比較前に補充した集合を版付きで保存する。

入力は同じ機械語画像に固定する。ソース・DWARF・compiler dumpは評価器側で使い、デコンパイラには選んだ入力プロファイルのbinaryだけを渡す。
compiler dumpで最適化の帰属を確認し、最適化フラグの有無の差と個別passの効果を分けて記録する。
元ソースの名前・型・構造には多対多対応や曖昧さを残し、回復可能な部分集合と対応精度を報告する。

manifestにはNirvana・compiler・solverの版、CPU機能、全フラグ、binary hash、入力seed、モデルID、解析上限を保存する。
同一環境で時間・最大RSS・出力量を測り、意味比較の状態、構造指標、失敗段階を入力ごとの同じ行へ結ぶ。
全RAMのdigestは補助観測として明記し、byte列の直接比較とは区別する。

**M0は部分的な評価手段が揃った段階**。完了条件は、上記の統合報告と構造評価器の対照検査を初回corpusで再現できることである。
初回corpus `nirvana-structure-initial-v1` の24構成を測定し、全件で固定ABIのnative↔IR・生成C比較を通した。baselineは`041a1e2`、開発集合で選んだ経路条件回復の比較先は`87bb55c`で、同じ24個のobject hashを確認した。開発用Clang O2のループ脱出例は構造距離25→15、goto 8→0、他の23構成のグラフは同じだった。22構成で正確な距離、2構成で探索上限付きの区間を得た。
次は、block内の処理と条件の内容を評価へ結ぶ部分を進める。各段階の検査根拠と適用前提の統合も継続する。

## M2で早期に扱う制御フロー変換

| 変換 | 回復候補 | 意味を保つ根拠 |
| --- | --- | --- |
| jump threading・処理の複製 | 同じ処理を領域へ集約し、前後の条件を組み直す | SSA入力と経路条件、実行される効果の順序・回数を照合する |
| 共通末尾・cross jumping | 共有先を必要な領域へ制限付きで複製する | 元PC対応と各経路のStepを検査し、動的な効果回数を保つ |
| loop rotation | 入口と末尾の判定を対応付け、while/forへ戻す | 初回条件・continue・出口・反復の対応を検査する |
| switch lowering | decision tree・表・bit testとcase/defaultを対応付ける | selectorの幅・値域と未知targetの残余、元のtarget評価を保つ |

これは[SAILR](https://www.usenix.org/conference/usenixsecurity24/presentation/basque)を参考にしたNirvanaの実装計画である。
候補は実行IR/CFGとSSA・MemorySSAから作り、受理後に影響する解析を更新する。
純粋な配置変更には既存の構造対応検査を使い、条件の変更やメモリ効果の移動には追加の意味検査を用意する。
元PC・fault・途中再開への対応を維持し、未知の辺が残る領域には局所gotoやdispatcherを置く。
採用範囲と探索予算を証拠に残し、同じM0報告で構造・意味・費用を比較する。
