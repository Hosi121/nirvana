# スタック位置の復元と名前付きメモリビュー

今回の到達点は、同じ機械語とメモリ契約のまま、O0の`sum`と`struct-fields`の
スタックアクセスを安定した名前で出力できることです。元の変数名・型・所有権の復元とは区別します。
速度の最適化、再配置・間接分岐への対応範囲の拡張は今回の対象に含めません。

## 位置の解析

`StackAnalysis::analyze(program, stack_register)`は、各レジスタの値を
「未知」「定数」「入口のスタックアドレス＋定数」のいずれかとして追います。
他の入力レジスタをゼロとは仮定しません。RBPも、RSPからコピーされたと確認するまでは未知です。

CFG上で合流する事実が一致したときだけ保持し、ループを含めて固定点を求めます。
入口への逆辺にも初期状態との合流を適用します。命令内の代入は順番に処理し、
一時レジスタの再利用やRSP変更の前後を区別します。オフセットの加減算はmodulo 2^64です。
`offset_before(address, assignment_index, expr)`で、その代入直前の式を問い合わせられます。

追う演算はコピー、定数の加減算、両腕が同じ事実を持つ純粋なSelectに限定します。
Loadを含むアドレス式は、どこに含まれていても置換しません。
例えば`select(load(invalid), rsp-8, rsp-8)`は、両腕の値が同じでもLoadを消せません。
動的なスタック移動、不一致の合流、メモリから取得したポインタは未知へ戻します。

解析には状態セル数100万、点数・ブロック処理回数・アクセス数各10万、式訪問200万、深さ256の上限があります。
上限に達した場合は途中の結果をすべて破棄します。Cで名前を付ける位置も最大256箇所に制限し、
それを超える場合は従来のアドレス式を使います。

## 高水準IRの表現とCへの接続

`hir::ViewPath`は、明示されたオブジェクト、バイトオフセットのフィールド、stride付き添字を表します。
`address`・`load`・`store`で既存IRへ下げられます。
これは型や配置を自動推定した結果ではありません。基底・添字の評価を省かず、
strideがゼロでもfaultする添字を消しません。独自のオブジェクト境界検査も追加しません。

CLIの`--emit readable-c`はx86のRSPを明示してスタック解析を有効にします。
ライブラリの汎用`emit_readable_c`はアーキテクチャを仮定しません。有効にする場合は
`emit_readable_c_with_options`へ`ReadableOptions { stack_register: Some(Reg(...)), ..Default::default() }`を渡します。
検査付き還元にも同じoptionsを受け取るAPIがあります。

生成例は次の形です。宣言で**入口時点**のアドレスを保存するので、途中でRSPが変わっても位置は変わりません。

```c
const struct nirvana_view stack_2 = {arg0 - 24};
v4 = nirvana_view_load(&m, stack_2, 8);
nirvana_view_store(&m, stack_2, 8, v4 + v3);
```

`nirvana_view_load/store`は従来の境界検査付きゲストメモリへ接続します。
ホストのローカル変数へ値を移す変換ではありません。同じ場所を未知のポインタから書いても、
次のLoadはその変更を読みます。異なる幅・異なる開始位置の重なりも、同じバイト列を共有します。
`ReadableC.stack_views`には位置、最大アクセス幅、潜在的な読み書き箇所数、他ビューとの重なりを記録します。
この幅はオブジェクトのサイズ保証ではありません。同じ位置を使い回す別の変数も、現段階では一つのビューです。

置換で不要になった純粋なアドレス計算は、出力で使うレジスタとすべてのメモリ式から依存関係を辿って除きます。
使われないLoadも残します。Cのストア右辺にLoadがある場合は、書き込み先の評価・範囲検査を
独立した文として先に出し、IRの「書き込み先を検査してから右辺を評価する」順序を保ちます。

## 同条件での比較

GCC 13.3.0、既存20ソース×O0/O2、同じC11・fno-lto設定のオブジェクトを使っています。
対応は従来と同じ33/40構成です。残る7構成の再配置は未対応のままです。

| 構成 | 名前付き位置 | 従来のLoad→生アドレスLoad＋名前付きLoad | Storeの同じ内訳 |
| --- | ---: | ---: | ---: |
| sum O0 | 5 | 15→1＋14 | 10→3＋7 |
| struct-fields O0 | 6 | 23→5＋18 | 12→3＋9 |

33構成で47箇所、潜在的な読み出し218箇所・書き込み58箇所を名前付きにしました。
O2の16構成は、このcorpusではスタックビューが0箇所です。
アクセスを削除した数ではありません。構造化による複製があると、生成C内の出現数と
IR内のアクセス箇所数は異なります。

これは**アドレスの表現範囲**の評価です。元ソースとの近さや復元精度を点数化した結果ではありません。
特に`struct-fields`も、`pair.left`などの型付きフィールドとしてはまだ出力しません。
高水準IRでfield/indexを表せること、配置を推定できること、型付きCへ出せることは別々に評価する必要があります。

```sh
python3 tools/build_fixtures.py
cargo run --quiet --example measure_stack_views -- target/stack-views
cargo run --quiet -- target/c-fixtures/cc-0/O0/sum.o --emit readable-c
```

比較表と前後のCは`target/stack-views/`に保存します。
`cargo test --test stack_views --test stack --test hir --test machine_pipeline`で主な回帰検査を実行できます。

## 検証境界と残る制約

- 33構成×63入力で、元C・元IR・還元IR・再コンパイルCの返り値と状態を比較します。
  IR間は全メモリの完全一致、生成Cは全メモリのダイジェストも比較します。
- 追加の生成C検査では、外部ポインタとのalias、重なる幅、入口後のSP変更、上限付近のアドレスを確認します。
- abortを捕捉し、最初に失敗したアドレスと停止前の全メモリをIRと比較します。
  書き込み先と右辺の両方が範囲外、Loadを含むSelectアドレス、使われないLoadをO0/O2・ビュー有無で確認します。
- スタック解析・ビュー置換・C用の代入除去はSMT証明の対象に含まれません。
  `--verify-reduction`が検査するのは従来どおりIR還元までです。
  [構造化の対応検査](structure-verification.md)もC整形前のASTまでで、C全体の証明ではありません。

一般的な型・構造体・配列の自動推定、スタック位置の生存期間による分割、メモリSSA、
Loadを跨ぐ値の伝播、スタックをホスト変数へ移す変換は未実装です。
生のC出力を含め、任意の式の複数LoadについてCの評価順を完全に検証したという主張もしません。

入力field/index、保存幅、局所値の共有を含む後続の改修は[memory-recovery.md](memory-recovery.md)を参照してください。
