# メモリを含む基本ブロックの検証

`block_verify` は、同じCFG境界を持つIR還元を独立に検査する。
モデルIDは `checked-memory-block-v1`。対象は[checked guest-memory契約](equivalence.md)で、
機械語のリフト、構造化AST、生成Cの正しさとは区別する。

## ブロックの関係

各ブロックの入口では、指定した入力レジスタと初期メモリが左右で一致するとする。
その他のレジスタには、左右で**独立した**任意の初期値を与える。
正常な出口では、次のアドレスまたは返り値、全メモリ、指定した出力レジスタを比較する。
Faultでは、読み／書き・アドレス・幅と、失敗までの全メモリを比較する。Fault時のレジスタは観測しない。

未観測レジスタを共有変数にしてしまうと、前のブロックで値が変わっていても検査が通る恐れがある。
独立な入力を使うことで、境界関係に必要な値を見落とすと局所検査が失敗するようにする。
局所反例はその境界関係への反例であり、関数入口から到達可能な状態とは限らない。

関数の検査では、変換前後のデータ依存から入口関係を提案し、後続ブロックの入口関係の和を出口の要求にする。
この依存解析は還元器のヘルパーを呼ばない。候補の新しい値がブロックをまたぐ場合は、対応表が未対応のため拒否する。
CFGの命令位置・長さ・静的制御先と入口が一致することも検査する。
到達可能な全ブロックで局所検査が通った場合に限り `Validation::accepted()` をtrueにする。

各ブロックは有限の命令列であり、反復回数を有限に切るループ展開は使わない。
正常な一遷移で同じ次ブロックの入口関係を保つ、という対応を全境界で検査する設計である。
合成の実装とこの対応付けは信頼する部分に含まれ、証明支援系での機械化はしていない。

## メモリと最初の失敗

- 初期メモリは64-bitアドレスからbyteへのSMT配列。初期値、base、sizeは任意。
- 1/2/4/8-byteのlittle-endianアクセスをselect/storeへ展開する。
- 範囲検査はIRと同じ、アドレス折り返し・base未満・幅・末尾の検査を符号化する。
- 代入は逐次処理する。storeは宛先の評価と範囲検査の後に値を評価し、全幅を一度に反映する。
- 最初のFaultだけを記録し、それ以降のメモリ更新とFault更新を無効にする。
- Selectは分岐ごとのガードで評価する。選択しない側のLoadはFaultを起こさない。
- Fault後のレジスタは観測しないので、不要な値は全域的な式としてよい。正常終了時のレジスタと、全てのメモリ効果は維持する。

メモリの違いを任意のアドレス `memory_witness` で探す。
そのアドレスも制約しないため、UNSATは全メモリの一致を対象にし、固定サイズのサンプル比較ではない。

## 反例の再実行と上限

SATの場合だけ、再実行用メモリを64 KiB以下に制限してモデルを取り直す。
全Load/Storeのbyteアドレスについて初期メモリの値を取得し、入出力のレジスタとともにIRで一ブロック実行して差を確認する。
再現できないモデル、再実行上限に収まらない反例、モデル取得失敗はUnknownにする。
**小さいメモリに制限した問い合わせからEquivalentを返すことはない。**

検査は最大64ブロック、各側4096レジスタ、式深さ256、訪問100,000ノード、byte観測4096箇所まで。
ソルバのタイムアウトに加えて、関数の検査で10秒を過ぎたら後続ブロックを開始しない。
実行中の問い合わせの停止・モデル抽出分の猶予は別にかかる。資源上限は未判定であり採用条件を弱めない。

## 再現

ソルバの準備は[純粋な式の検証](pure-expression-verification.md)を参照する。

```sh
NIRVANA_Z3=target/verification-venv/bin/z3 cargo test --test block_verification -- --include-ignored
python3 tools/build_fixtures.py
cargo run --example verify_reductions -- --z3 target/verification-venv/bin/z3
```

最後のコマンドは既存fixtureのO0/O2オブジェクトからIRを作り、実際の還元結果を検査する。
`target/block-verification/` に問い合わせと結果を保存する。未対応・時間切れは元IRを保持する側に数える。
この例の終了コード0はレポート生成の成功を意味し、全構成の検証成功を意味しない。
原デコーダやC生成の検証済みという意味ではない。

## 還元器とC出力への接続

`reduce_checked` は通常の還元器が作った候補を検査器に渡す。
全ブロックがEquivalentUnderModelの場合だけ候補を返し、それ以外は**関数全体の元IR**を返す。
部分的に通ったブロックだけを混ぜて使わない。元IR保持時の統計は元の代入数と0 passesにする。
元IRを使う場合は初期レジスタ全要素を値引数に渡し、未初期化のローカルへ置き換えない。

`emit_readable_c_with_checked_reduction` とCLIの `--verify-reduction` から利用できる。

```sh
cargo run -- target/c-fixtures/cc-0/O2/diamond.o --emit readable-c \
  --verify-reduction target/verification-venv/bin/z3
```

標準エラーにIR還元の採否とモデル名を出す。ソルバ欠如、未判定、局所反例でも元IRからCを出力する。
このオプションはIR還元の検査であり、構造化やC生成の検査を兼ねない。
基本の構造化ASTには別の[対応検査](structure-verification.md)が常に適用される。
C用の整形とC生成は引き続き別の検証範囲。
通常の `--emit readable-c` はソルバを起動せず、従来の実行比較済みパイプラインを使う。

## 実際のfixtureでの結果

GCC 13.3.0、従来と同じ20ソース×O0/O2のうち、機械語からIRへ変換できた33構成を検査した。
各SMT呼び出しの上限は2秒。30構成の還元を採用できた。
未判定構成の途中分も含め、計159ブロックの問い合わせがUNSATになった（採用した30構成では154ブロック）。
残る `sum -O0`、`arithmetic -O0`、`struct-fields -O0` は検査が時間切れとなり、元IRを保持する。
採否は使用ソルバと予算にも依存し、未判定を誤変換とは断定しない。
7構成のフロントエンド未対応は従来どおり別に記録する。

採用経路ではdiamond・sum・外側ループへの脱出、元IR保持経路ではarithmeticの生成Cを
各63入力で元C・IRと比較する。全メモリはIR間ではbyte列、生成Cではダイジェストも検査する。

回帰検査には、全アクセス幅でのstore→load転送、遅延Load、メモリalias、失敗前の異なる書き込み、
読み／書きFaultの違い、store宛先と値の評価順、ループ境界を含める。
IRの `run_block_with_memory` は後続ブロックに入る直前で止まり、具体反例の再実行に使う。

信頼する部分はSMTエンコーダ、ソルバ、境界の合成処理。UNSATの独立証明書検査は未実装。
配列の意味は[Z3のselect/store仕様](https://microsoft.github.io/z3guide/docs/theories/Arrays/)を参照する。
