# 共有末尾の配置を改善する

今回の目標は、コピー上限と意味保存の条件を変えずに、構造化できる範囲と静的な複製数を改善すること。
処理時間の高速化とは分けて評価する。

## 後支配だけでは末尾が複製される場合

複数の枝が同じ末尾へ進んでも、その途中に別のreturnがあると、その末尾は分岐元を後支配しない。
また、機械語では複数のreturnが共通のエピローグへまとまり、共有したい計算より先が直接後支配者になる場合もある。
従来の構造化では各枝の中に末尾を置くため、同じブロックの3回目の配置で既定上限2に達することがあった。

例えば手書きIRのcopy-limitは、今は次の形になる。

```c
if (cond1) {
    value = 10;
} else if (cond2) {
    value = 20;
} else if (cond3) {
    value = 30;
} else {
    return 111;
}
return value + input;
```

最後の計算を一回だけ配置する。条件式や代入順、元の命令アドレス列は変更しない。

## 二つの候補を比較する

まず従来どおり、支配・後支配と自然ループでASTを作る。複製なしで成功した場合はそれを返す。
複製があるか構造化が失敗した場合だけ、追加の候補を作る。

追加候補では、支配関係で識別したバックエッジを除いた、可約CFGの前向きのDAGを作る。
分岐の両側から到達できる頂点を探索し、近い共通の後続を合流候補にする。
探索は現在の領域の終端を越えず、現在のループの外へは進めない。
内側の分岐では、すでに決めた外側の合流点も終端として引き継ぐ。
これによりreturnする枝をそのまま終わらせ、残る枝を共有末尾へ集められる。

これは候補生成のヒューリスティックであり、最適解を求めるアルゴリズムではない。
候補は[独立した構造検査](structure-verification.md)を通る必要がある。
元のCFGを変更して検査を通すことや、誤差・未判定を成功扱いすることはない。

- 両方が成功した場合は、ブロック配置数と元命令配置数の両方が増えず、少なくとも片方が減る候補だけを採用する。
- 従来が失敗し追加候補が成功した場合は、同じコピー上限内でその候補を採用する。
- 追加候補が失敗した場合は従来の結果を使う。両方失敗なら従来の理由でgotoへ戻す。
- コピー上限は引き続きブロックごとに2。1を指定すれば複製は禁止する。
- 追加探索は一関数につき100,000頂点訪問まで。超えた場合は候補探索を打ち切り、既存の結果へ戻せる。

従来戦略と追加戦略は、同じ支配・後支配の計算結果を共有する。
既存のASTに後から継ぎはぎするのではなく、各候補を入口から作り、候補全体を検査する。

## 同じ入力での比較

比較元は23b94bf、比較先は今回の変更。GCC 13.3.0、同じfixtureオブジェクト、同じ既定コピー上限2を使った。

| 対象 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 4命令CFG 4,000個の構造化成功数 | 3,859 | 3,859 |
| 上記の余分なブロック配置 | 20 | 12 |
| 上記の全元命令配置 | 7,865 | 7,857 |
| 実機械語33構成の構造化成功数 | 30 | 32 |
| 従来から成功する30構成の元命令配置 | 983 | 960 |
| 従来から成功する30構成の余分なブロック配置 | 7 | 3 |
| short-circuit O2の元命令配置 | 49 | 31 |

新しく成功したのはcopy-limit O0とshort-circuit O0。
32構成全体の配置数は、新たに対象に入った構成も足すため1,071になる。983との単純比較はしない。
残るgotoは、複数入口の循環を持つirreducible O0。SCCの入口分割などは今回行わない。
再配置が必要な7構成のフロントエンド未対応は変わらない。

全成功例の既定コピー上限と独立検査を維持する。
新しい専用テストでは、部分合流点とメモリへの書き込み、Faultし得る早期returnを組み合わせ、
入力・メモリ領域・実行上限を変えて元IRとASTの全実行状態を比較する。
変更後の全139テスト（SMTの6テストを含む）、Clippyの警告エラー設定、rustfmtを通過した。

## 再現とコスト

```sh
cargo run --release --example measure_structure -- target/join-optimization/current
```

4,000個の全結果をtiny.tsv、機械語40構成の結果をfixtures.tsvに保存する。
構造化失敗・フロントエンド未対応も行に残すので、成功したものだけを抜いて比較しない。
今回のbefore/afterと比較集計はtarget/join-optimizationに保持している。

追加の候補生成と検査にはコストがかかる。releaseで4,000個を一回ずつ処理した今回の観測は約37→42ms。
環境変動を除くベンチマークではなく、高速化の証拠にはしない。
今回の採用理由は構造化範囲と複製数の改善であり、解析速度の改善ではない。
