# コピーを考慮した局所変数の割り当て

今回の問いは、返り値・全ゲストメモリ・faultを保ち、計算結果を別変数へ渡すだけの代入を減らせるかです。
前回の`f1d7694`を基準に、保存場所の割り当てだけを変更しました。式の伝播やLoadの移動は行いません。

## なぜコピーが残っていたか

従来は、代入先が書かれる時点で生きている他の局所値すべてを、同じ保存場所へ置けない組として扱いました。
ただし`destination = source`の直後は、両者が生きていても同じ値です。
そのコピー自体を理由に保存場所を分けると、以後別々の箇所でしか使わない値でもコピーが残ります。

コピーを行うその代入に限って、sourceとの衝突を追加しない候補を作ります。
sourceまたはdestinationを後で別の値へ書き換える箇所では、通常の生存性に従う衝突を引き続き追加します。
同じ式・条件・storeで同時に読む別レジスタも分離します。
この保守的な制限は、共有後にCで`x == x`のような自己比較が突然現れることも避けます。

## 候補の選び方

既存の厳しい衝突グラフと、同じ順序・同じ色選択を使うgreedy割り当てを先に求めます。
その結果を保持し、別の資源予算でコピーを考慮した候補を求めます。
コピーでつながる値について、使える色の中からコピー回数の重みが最大になる色を優先します。
重みが同じなら小さい色番号を使い、入力のeligible列の順序によらない決定性を保ちます。

候補は、保存場所が少ない場合、または同数で残るコピーが少ない場合だけ採用します。
候補の資源が尽きた場合も従来の結果を返します。保存場所の数を増やす変更は採用しません。
入口で生きているeligible値、不正・重複したeligible番号、従来の解析の資源超過では、従来どおり`None`を返します。

readable Cでは同じ保存幅の値だけで割り当てます。引数・ビュー・評価順序用のprivate temporaryを共有する変更ではありません。
同じC名になった`a = b`は既存の出力処理が省き、既存の複合代入表示も利用できます。
元IR、構造化ASTのcertificate、全レジスタを観測する`--emit c`の契約は変更しません。
同じ保存場所にした後の最終レジスタファイル全体は、元レジスタとの比較対象ではありません。

## 同じ機械語での結果

既存20ソースとrecovery 6ソースを、GCC 13.3.0のC11・Wall/Wextra/Werror/pedantic・fno-lto・O0/O2で比較しました。
52構成のうち同じ45構成が対応し、7構成は従来どおり再配置を拒否します。
前後45本ずつの生成Cは、同じコンパイル条件を通っています。

| 計測 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 局所変数間の単純コピー文 | 33 | 15 |
| 数値局所変数の宣言 | 155 | 149 |
| 関数内トークン合計 | 15,316 | 15,218 |
| 関数全体のbyte数 | 76,623 | 76,007 |

局所値の数が増えた構成はありません。goto・mask・castの合計は変わりません。
コピー数は生成Cの`valueN = valueM;`形式の文を数えます。IRコピー数や実行回数そのものではありません。
ソースとの類似度・一般の復元精度・実行速度を測った値ではありません。

| 個別例 | コピー文 | 数値局所変数 |
| --- | ---: | ---: |
| `early-exit-chain O2` | 9 → 4 | 8 → 7 |
| `sum O2` | 4 → 1 | 5 → 3 |
| `three-entry-goto O2` | 4 → 1 | 7 → 6 |
| `nested O2` | 1 → 0 | 2 → 1 |

例えば`early-exit-chain O2`では、添字から読む値を別変数へコピーせず、
アキュムレータや添字を直接更新できるようになります。以下は実際の本文の一部です。

```c
value5 = read64(element(input.base, (value3 + value2) & 3, 8));
if ((value5 & 7) == 3) {
    value1 ^= value5;
    break;
}
value1 = value1 + value2 + (value5 >> 1);
```

## 検証と再現

既存の割り当て検査は、eligible値を新しいレジスタ群へ独立に付け替えてIRを再実行します。
新しい群にはpoison値を入れ、返り値だけでなくfault・全メモリ・trace・停止位置・step limitを比較します。
初期化されていない値を偶然同じゼロで読む誤りや、ループの逐次コピーによる上書きを検出するためです。
native側も、既存3 corpusの元C・IR・再コンパイルCの比較と、最初のfaultアドレス・停止前メモリの検査を維持します。

独立に追加した7検査は、コピー後のsource/destination上書き、合流、ループの逐次交換、
メモリアドレスと値のコピー、alias・部分書き込み・最初のfault、eligibleの部分指定、到達不能な入力使用を含みます。
固定seedの24 CFG × 6初期値 × 7命令数上限の1,008組を含め、計1,558組で完全な観測値を照合しました。
全eligible値を一つの場所へ置く誤った割り当てでは、期待する返り値6に対して0になり、検査が差を検出します。
同じ保存場所を使わない元レジスタの値も追加検査では照合しています。

3つのnative corpusでは61/68構成、3,979入力比較が通過しました。
生成16構成はUBSan付きの1,008入力比較も一致し、診断はありません。
任意SMT9件を含む全290テスト、Clippy警告ゼロ、rustfmtを確認しています。
SMTの検証範囲は従来のモデルまでで、今回の割り当ての普遍的な同値証明ではありません。

```sh
cargo test --test allocation --test copy_allocation
NIRVANA_Z3=target/verification-venv/bin/z3 cargo test --all-targets -- --include-ignored
cargo build --bin nirvana
python3 tools/compare_readable_output.py --before /path/to/f1d7694/nirvana --out target/copy-flow
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

`target/copy-flow/comparison.json`には各構成の値、コンパイラ情報、ソース・機械語・両CLIのSHA-256を残します。
同じ場所に前後のC全体・関数部分・全テストログを保存します。これらはGit管理せず、検査と生成道具をコミットします。
保存場所の割り当て全体やC出力全体の形式証明を追加したものではありません。
元ソースの変数名・型や、ループ全体のSSAを復元する変更も今回の範囲には含めません。
